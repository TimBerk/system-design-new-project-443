# Индекс истории пассажира (passenger_id, created_at DESC)

## Контекст и проблема

Цель истории: p95 ≤ 50 мс при 2 000 000 поездок в базе. Базовый замер [reports/baseline.md](../../reports/baseline.md) показал нарушение: p95 = 106,36 мс, и даже самый быстрый ответ — 61,5 мс — выше цели. План запроса объяснял почему: Parallel Seq Scan по всей таблице `trips`, ≈2 000 000 прочитанных строк и 54 229 страниц буферов (~423 МБ) ради 20 строк, выполнение 61,3 мс — задержка целиком в базе. Операция чтения фиксирована запросом:

```sql
SELECT ... FROM trips WHERE passenger_id = $1 ORDER BY created_at DESC LIMIT 20
```

Состав индекса должен следовать из этого запроса: равенство по пассажиру — первым полем, сортировка по времени — вторым.

## Какие варианты сравнивали

- **Сохранить прежнюю схему без индекса.** Отказ: замер baseline подтверждает нарушение цели — каждый просмотр истории читает всю таблицу из 2 млн строк.
- **Индекс только по пассажиру — `(passenger_id)`.** Убирает Seq Scan: фильтр находит ≈200 строк нужного пассажира. Но `ORDER BY created_at DESC` остаётся отдельным шагом сортировки найденных строк, и его работа растёт вместе с историей одного пассажира. Отказ: индекс обслуживает только половину операции чтения — фильтр без сортировки.
- **Составной индекс `(passenger_id, created_at DESC)`.** Равенство первым полем обслуживает `WHERE`, второе поле повторяет `ORDER BY`, поэтому `LIMIT 20` останавливает чтение на первых записях индекса. Принят.

## Решение

Миграция [db/migrations/007-history-passenger-index.sql](../../db/migrations/007-history-passenger-index.sql) создаёт `trips_passenger_created_at_idx` на `trips (passenger_id, created_at DESC)`. Порядок полей взят из наблюдаемого запроса истории: условие равенства ведёт индекс к нужному пассажиру, направление второго поля совпадает с сортировкой списка.

## Последствия

- план переключился на Index Scan — 20 прочитанных строк и 26 страниц буферов (~208 КБ) на запрос вместо ≈2 000 000 строк и ~423 МБ;
- сортировка исчезла;
- выполнение 0,242 мс вместо 61,3 мс;
- p95 истории упал со 106,36 мс до 3,08 мс;
- цель ≤ 50 мс выполняется с запасом ([reports/after-index.md](../../reports/after-index.md), сравнение с [reports/baseline.md](../../reports/baseline.md)).

Цена:
- **Дополнительный объём хранения**: индекс занимает 60 МБ при таблице `trips` в 423 МБ (замер `pg_relation_size` на 2 млн строк) и растёт вместе с таблицей.
- **Дополнительная работа при записи**: каждый INSERT поездки и UPDATE её статуса поддерживает ещё одну индексную структуру. На повторном прогоне создание поездок шло заявленными 5/с без ошибок и пропущенных итераций — заметной деградации записи не наблюдалось.

Откат:
- `DROP INDEX trips_passenger_created_at_idx`.
- Признак для отката — замер показывает, что запись поездок деградировала сильнее, чем выиграла история, либо план перестал использовать индекс (в EXPLAIN снова появился Seq Scan).

## Подтверждение

Два прогона одним профилем mixed (5/20/5, разогрев 10 с, длительность 30 с) на одном наборе данных (2 000 000 поездок из `make seed-large`):

- до — [reports/baseline.md](../../reports/baseline.md),
- после — [reports/after-index.md](../../reports/after-index.md). 

Оба прогона безошибочные (0%) и без пропущенных итераций (dropped_iterations = 0), значит сравнение валидно. Повторный EXPLAIN на тех же данных показывает Index Scan без чтения таблицы целиком.
