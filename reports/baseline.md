# Замер baseline

## Условия опыта

- ядер у docker: 12
- память docker: 16 770 088 960 байт (≈15,6 ГБ)
- лимиты app: 500 000 000 nanocpus (0,5 CPU), 536 870 912 байт (512 МБ) на экземпляр
- сценарий: load/mixed.ts
- профиль: load/profile.json
- данные: 2 000 000 поездок у 10 000 пассажиров (по 200 поездок у каждого)

## Итоги прогона

| Показатель         | Значение                | Цель    | Статус                     |
|--------------------|-------------------------|---------|----------------------------|
| p95 истории        | 106,36 мс               | ≤ 50 мс | цель нарушена (в 2,1 раза) |
| Доля ошибок        | 0 % (0 из 952 запросов) | ≤ 0,1 % | в бюджете                  |
| dropped_iterations | 0                       | 0       | частота подана полностью   |

Распределение истории: среднее 84,08 мс, медиана 83,36 мс, минимум 61,5 мс, максимум 160,19 мс. Даже самый быстрый ответ истории превышает цель 50 мс — нарушение устойчивое, а не хвост распределения.

### План запроса

```sql
Limit  (actual time=57.864..61.169 rows=20 loops=1)
  ->  Gather Merge  (Workers Launched: 2)
        ->  Sort  (Sort Key: created_at DESC, top-N heapsort)
              ->  Parallel Seq Scan on trips  (actual time=1.153..53.008 rows=66.67 loops=3)
                    Filter: (passenger_id = 1)
                    Rows Removed by Filter: 666650
                    Buffers: shared hit=15808 read=38345
Execution Time: 61.325 ms
```

- Тип чтения таблицы: **Parallel Seq Scan** — база последовательно читает всю таблицу `trips`, потому что индекса по `passenger_id` нет.
- Число прочитанных строк: **≈ 2 000 000** — Rows Removed by Filter 666 650 × 3 воркера; пригодилось ≈ 200 строк пассажира, клиенту отдано 20.
- Буферы: `15 884 hit + 38 345 read = 54 229 страниц по 8 КБ` ≈ **423 МБ на один просмотр истории**.
- Время выполнения 61,3 мс совпадает с минимальным временем ответа истории в прогоне (61,5 мс).

## Вывод

Цель истории нарушена - `p95 = 106,36 мс` при цели ≤ 50 мс, при этом даже минимум (61,5 мс) выше цели. Причина в последовательном чтение всей таблицы из 2 млн строк (~423 МБ буферов), фильтрации до ~200 строк пассажиров и сортировки top-N ради 20 строк. Замер валиден - ошибок 0 % и dropped_iterations = 0.
Узкое место в чтении истории в PostgreSQL, а не приложение или балансировщик: быстрые операции (чтение состояния, создание) укладываются в единицы миллисекунд, медиана всех запросов 1,75 мс.

## Гипотеза

Составной индекс `trips (passenger_id, created_at DESC)` сократит работу базы:

- поле `passenger_id` обслуживает `WHERE passenger_id = $1` — Index Scan сразу находит ≈200 строк пассажира вместо чтения всех 2 млн;
- поле `created_at DESC` совпадает с `ORDER BY created_at DESC` — строки уже идут в нужном порядке, сортировка не нужна: LIMIT 20 возьмёт первые 20 записей индекса и остановится.

Ожидание: вместо ≈2 000 000 прочитанных строк и ~54 тысяч страниц буферов база прочитает ~20 строк из индекса, время запроса упадёт с ~61 мс до единиц миллисекунд, p95 истории уйдёт ниже цели 50 мс. Проверка — [ADR-010: индекс истории](../design/adr/010-history-index.md) и повторный замер [reports/after-index.md](after-index.md) на тех же данных.
